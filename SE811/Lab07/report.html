Bringing Codeface back from the dead

Codeface was archived in 2022 and targets Ubuntu 14.04, Python 2.7, R 3.x and MySQL 5.5. Its documented install path is not merely awkward on a 2026 machine — it is impossible. This is what it took to make it run again, and the four defects that surfaced on the way.

Three latent bugs in Codeface itself were found and fixed along the way.

Why it doesn't run today

The documented path is vagrant up against an Ubuntu 14.04 box. That path is dead, for three independent reasons:

  • install_repositories.sh hard-aborts on anything that isn't 14.04 or 16.04.
  • Both releases are past end-of-life — I confirmed their archives no longer resolve (old-releases.ubuntu.com/.../xenial → 404).
  • The stack it wants — Python 2.7, R 3.x, MySQL 5.5 (Travis explicitly downgrades 5.6 → 5.5) — has no counterpart on a host shipping Python 3.12 and no R at all.

So the task isn't "install the dependencies". It's: decide which era to reconstruct, find which pieces of that era still exist, and rebuild the rest.

The detail that decided it

util.py:check4ctags() asserts the ctags version string starts with Exuberant Ctags 5.9~svn20110310 and raises otherwise. Bionic ships exactly 1:5.9~svn20110310-11ubuntu0.1. Any modern distro ships universal-ctags, where this check can never pass — proximity tagging would be unusable without patching Codeface.

Scoping the R dependency set

Upstream packages.r installs ~45 packages and is unusable as written: it calls biocLite() (retired 2019), installs from live CRAN HEAD (requires R ≥ 4.x), pulls four packages from GitHub, and passes dependencies=TRUE.

Rather than install all 45, I computed the transitive source() closure of the three scripts codeface run actually executes. That reaches 23 R files needing 33 libraries — the mailing-list-only packages aren't on this path at all. Parsing the pinned CRAN index then showed why the upstream flag is fatal:

1,544Closure with dependencies=TRUE (incl. Suggests)
96Closure with hard dependencies only
~8 minResulting install time on 12 cores

A tempting shortcut was rejected: Michael Rutter's c2d4u3.5 PPA is still alive with 6,201 prebuilt r-cran-* debs. But they're built against R 4.4 while we run 3.6.3 — beyond the ABI mismatch, R 4.x flips the stringsAsFactors default and carries a decade of igraph API drift. That's the class of breakage that quietly corrupts results from 2013-era code rather than failing loudly.

The four defects

Each failure below is tagged by origin: whether it was a bug in Codeface itself, in my own scaffolding, or an environmental casualty of the choices above.

1 · libglpk.so.40: a package that "installed" but could not load

Environmental Fixed 
Error: package or namespace load failed for 'igraph' in dyn.load(...):
 unable to load shared object '.../igraph/libs/igraph.so':
  libglpk.so.40: cannot open shared object file: No such file or directory
ERROR: required packages failed to install: igraph, markovchain, BiRewire

markovchain and BiRewire were collateral damage — both depend on igraph. The log line * installing *binary* package 'igraph' corrected an assumption I'd made: 97 of 101 packages arrived as prebuilt binaries. Posit's index advertises source tarballs, but downloads are content-negotiated on the R User-Agent.

The consequence is subtle: install.packages() reported success. A prebuilt binary is unpacked, never linked, so a missing shared-library dependency isn't detected at install time — it surfaces later at dyn.load(). I confirmed the exact requirement by downloading the artefact Posit actually serves and reading its ELF headers: 

$ objdump -p igraph/libs/igraph.so | grep NEEDED
  NEEDED  libxml2.so.2     NEEDED  libgmp.so.10    NEEDED  libglpk.so.40
  NEEDED  liblapack.so.3   NEEDED  libblas.so.3    NEEDED  libgfortran.so.4

Fixed with an APT layer for the missing libraries, placed immediately before the R package layer so the expensive earlier layers stayed cached. I also changed the verifier to print the actual dyn.load message per failing package, so the next iteration wouldn't need the same forensics.

2 · npm missing — a failure my own Dockerfile hid

My scaffolding Fixed

The first bootstrap ended with npm: command not found — even though the image built successfully. The cause was my own line:

RUN apt-get install -y --no-install-recommends nodejs npm && ... || true

The trailing || true applies to the whole && chain, swallowing a real apt failure that had been sitting in the build log all along:

npm : Depends: node-gyp (>= 0.10.9) but it is not going to be installed
E: Unable to correct problems, you have held broken packages.

--no-install-recommends prevents node-gyp's dependencies from resolving. Rather than drop the flag, I installed the official Node 14.21.3 tarball — the newest line still running on bionic's glibc 2.27, bundling npm 6.

Lesson recorded

Never terminate a Dockerfile RUN chain with || true. It converts a build failure into a runtime failure far from its cause.

3 · svglite: a dependency no static analysis can find

Environmental Fixed 
[codeface.R] CRITICAL: there is no package called 'svglite'
  4: ggsave(file.path(graphdir, "ts_commits.svg"), g, width = 12, height = 8)
  6: svglite::svglite

svglite appears nowhere in Codeface's source. I re-scanned the whole run-path closure for library(), require(), requireNamespace() and pkg:: references; the only namespace-qualified package is igraph. The dependency is indirect: ggsave() dispatches on the .svg extension to svglite::svglite at runtime, and ggplot2 declares it only under Suggests — precisely the field my dependency restriction dropped.

So the 16× build-time saving had exactly one casualty, and it was invisible to static analysis. The general lesson: a source-derived dependency closure is a lower bound; runtime dispatch escapes it.

4 · Upstream bug: project configs cannot enable sloccount

Codeface bug Patched

The run succeeded but sloccount_ts was empty. At --loglevel devinfo the config showed sloccount : FALSE — even though the project file says sloccount: true. The cause is in R/config.r::load.config: 

if(is.null(conf$understand)) { conf$understand <- FALSE }
if(is.null(conf$sloccount))  { conf$sloccount  <- FALSE }
...
conf <- c(conf, yaml.load_file(project.file))    # appends, does not merge

Defaults are applied to the global config before the project file is merged, and c() concatenates lists rather than merging them. The result holds two elements named sloccount, and conf$sloccount returns the first — the default FALSE. So sloccount: true in any project config was silently discarded and the complexity analysis always returned early.

The Python side doesn't share the bug: configuration.py uses dict.update(), which replaces correctly. Patched to replace duplicate keys instead of appending — after which the stage reports Analysing 41 code samples.

5 · Upstream bug: sloccount races itself under -j > 1

Codeface bug Patched

With sloccount finally enabled, only 6 of 41 samples reached the database. sloccount alone worked fine, and so did two sequential runs. Running four concurrently reproduced it instantly: 

mkdir: cannot create directory '/root/.slocdata': File exists
run1 EXIT=1  run2 EXIT=1  run3 EXIT=1  run4 EXIT=1

gather.sloccount.results() invokes sloccount without --datadir, so every instance uses the single default ~/.slocdata. It's called from inside mclapply.db(), so with -j > 1 the instances race and all but one abort. The failures were invisible because do.system discards stderr — the only symptom was a sparsely populated table.

Patched to give each invocation its own data directory. One wrinkle found by testing: sloccount requires the directory to already exist. Verified — four concurrent runs all exit 0, and the stage now writes 41 of 41 samples.

The web frontend

The frontend serves on http://localhost:8081/, driven by the same database the analysis populated — but not by the documented route. docs/webserver.md instructs you to install a custom fork of shiny-server (JohannesEbke/shiny-server, branch no-su) into a bundled Node.js 0.10.13 — a 2013 runtime that no longer builds, from a fork that has since disappeared.

That route is also unnecessary: codeface dynamic runs the same Shiny apps directly through R's own built-in web server, with no Node involved. Two packages were still missing:

PackageUpstream sourceStatus
shinybootstrap2install_github("rstudio/shinybootstrap2")That repo now 404s — but it is on CRAN, so the pinned snapshot supplies it (0.2.1)
shinyGridsterinstall_github("wch/shiny-gridster")Genuinely GitHub-only; still alive. Installed from a source tarball rather than pulling the whole devtools tree into the image

Every Shiny app wraps its UI in shinybootstrap2::withBootstrap2(), so without it all six apps fail. shinyGridster is needed only by dashboard.

But one app is not enough. codeface dynamic calls runApp(), which mounts a single app at /. The breadcrumb navigation uses relative links — breadcrumb.config.r builds "../dashboard/?projectid=2" — so selecting a project resolves to a path that doesn't exist and returns 404. Each app must be mounted under its own URL path beneath a shared parent, which is exactly what site_dir + directory_index in shiny-server.config was for.

The official Shiny Server understands that same configuration and RStudio still publishes a bionic build (1.5.20.1002), so it replaces the dead fork — with two adaptations: absolute paths (the original site_dir is relative to the checkout), and a run_as directive, which the original omits. Shiny Server only warns about run_as root at startup, then hard-refuses at request time with Aborting attempt to launch worker process as root — surfacing as an HTTP 500 with empty app logs.

A third upstream defect: three apps ship no global.r

Codeface bug Patched

With routing fixed, projects, dashboard and details returned 200 — but plots, timeseries and timezones returned 500 with empty logs. Run directly: 

Warning: Error in breadcrumbOutput: could not find function "breadcrumbOutput"
  53: shinybootstrap2::withBootstrap2

The three working apps each ship a global.r that sources common.server.r — which defines the navigation helpers and the global conf/projects.list objects. The three failing apps have no global.r at all: their ui.r sources common.ui.r, so the UI loads but the first render dies. Adding the missing file to each fixes all three.

Verifying it actually renders

An HTTP 200 proves only that the initial HTML was served — Shiny fills the page over a websocket afterwards, so a broken app still returns 200. Driving a real session over Shiny Server's SockJS transport failed twice for reasons that both look like server faults and are not:

  • A raw websocket to /apps/projects/websocket/ never opened — that endpoint belongs to standalone runApp(); Shiny Server uses /apps/<app>/__sockjs__/<server>/<session>/.
  • Plain SockJS to that path got o then an immediate c[1000,"Normal closure"]. The server log gave the reason: Invalid multiplex packet received. Shiny Server wraps SockJS in its own multiplex layer — every frame is <id>|<method>|<payload>.

With correct framing the app returns its rendered outputs:

output$quantarchBreadcrumb   ->  "Codeface projects  /  flask"
output$selectionlistelements ->  "Open Source Projects  /  flask"
Usability trap

Because Shiny Server mounts each app under its own path, http://localhost:8081/ serves a bare directory listing, not the UI. Opening the root and seeing no application is the most likely reason to conclude the frontend is broken when it is fine. A small index.html landing page now redirects the root to apps/projects/.

Codeface's own test suite

Integration (test_exampleprojects): 4/4 passed in 81 s. Unit: 28/29. The single failure is test_cppstats_works — cppstats is only needed for feature tagging, not the proximity tagging used here, and it is no longer installable at all: install_cppstats.sh fetches srcML from http://131.123.42.38/…, a host that now times out.

per_cluster_statistics remains empty. This is expected upstream behaviour, not a defect of this setup: Codeface's own integration test lists that table under ignore_tables with the comment # TODO: Check if these should be filled. Every table upstream does expect is populated.

Limitations

  • Mailing-list analysis (codeface ml) was not attempted — it needs snatm and tm.plugin.mail from GitHub forks. Flask coordinates on GitHub, so there was nothing to analyse, and codeface run doesn't touch this path.
  • Feature tagging is permanently unavailable — srcML's download host is dead.
  • The web frontend runs, but not by the documented route — the shiny-server path in docs/webserver.md is dead.
  • Conway analysis requires a JIRA tracker and Titan jars — not applicable to Flask.
  • The container runs as root, so files it writes into the bind mount are root-owned on the host.
